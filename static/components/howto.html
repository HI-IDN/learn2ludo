How It Works

A plain-language guide to how bots make decisions in Learn2Ludo.

Before a bot can decide anything, it needs to know what is happening on the board. The game state — written x — is a complete snapshot of the game at one moment in time. It contains:

  • Every pawn's current position (yard, track, home stretch, or finished)
  • Whose turn it is
  • The dice value just rolled
  • Which moves are currently legal
  • Board layout — track length, safe squares, starting squares
Think of the game state as a photograph of the board. Two identical photographs mean two identical situations — and a deterministic bot will always make the same choice given the same photograph.

Raw board positions are hard to reason about directly. Features translate a game state x into a set of numbers — one per candidate move — that capture what matters strategically. Each feature answers one question about what happens if you make that move. We collect them into a vector φ(x), one entry per feature.

Raw features (before normalisation)

Capture {0, 1}
Does this move land on an opponent's pawn and send it back to their yard? 1 if captures, 0 otherwise
Risk ℤ ∈ [0, 6]
Number of unique dice rolls that would allow any opponent to land on this square next turn. 2 — two different rolls threaten the destination
Risk reduction ℝ ∈ [−1, 1]
Decrease in risk exposure compared to staying put. Negative means the move increases danger. −0.17 — landing here is riskier than the current square
Progress ℤ⁺
Target position index along the track (higher = closer to home). 6 — moves to position 6 of 52
Safety {0, 1}
Does the destination land on a safe square or home stretch? 1 on a safe haven, 0 on a normal square
Blockade {0, 1}
Does this move stack with a friendly pawn, blocking opponents from passing? 1 if two friendly pawns share a square
Spread ℤ⁺ ∈ [0, T/2]
Mean pairwise circular distance (in cells) between your active pawns after the move. T = track length. 18 cells average — pawns spread across the board
Activation {0, 1}
Does this move bring a pawn out of the yard for the first time? 1 when a yard pawn first enters the track
Type notation: {0, 1} binary — 1 = True, 0 = False [0, 1] normalised real ℝ real (pos. or neg.) ℤ integer ℤ⁺ positive integer

These 8 features are just a starting point — there can be many more. You can also construct new features by combining existing ones mathematically:

capture − risknet gain — rewards capturing only when the landing square is not immediately dangerous
progress × safetysafe advancement — only values progress that lands on a protected square
spread + activationboard presence — encourages distributing pawns while also entering new ones
(1 − risk) × progressrisk-adjusted advancement — discounts progress on exposed squares

Features arrive on different scales — Capture is binary, Progress can be any positive integer, Risk sits between 0 and 6. Before a weighted model can use them, every feature must be mapped to the same range, [0, 1]. Without this step, a weight of 0.8 on Capture would not be comparable to 0.8 on Progress.

Once all features land in [0, 1], a weight of 0.8 on Capture carries exactly the same magnitude as 0.8 on Progress. The scale is shared, so weights are directly comparable across every feature.

All features above evaluate the board state after the move — they are all 1-step lookahead. For example, Capture asks "if I move here, is there an opponent to send home?" rather than "is there currently an opponent nearby?". This is a subtle but important distinction:

Current-state feature
  • Evaluates the board right now
  • Example: "does this pawn currently sit on a safe square?"
  • Does not account for what the move changes
1-step lookahead feature
  • Evaluates the board after making this move
  • Example: "does making this move land on a safe square?"
  • All 8 Learn2Ludo features work this way
The pawn preview you see on the board is 1-step lookahead visualised — it shows you the state that would result from each candidate move.

Some features naturally require comparing two states — current and future. For example, "does this move break an existing blockade?" requires knowing whether a blockade exists now and whether it dissolves after the move. Going further is also possible:

2-step lookahead
  • For each candidate move, simulate all opponent replies
  • Score the board after the opponent's best response
  • More accurate — but cost multiplies with each step
Monte Carlo simulation
  • Play out thousands of random games from the resulting state
  • Use the win rate as the feature value
  • Rich signal — natural path toward full RL

The 8 features in Learn2Ludo are just a starting point. Good features are concrete (computable from the game state), measurable (produce a number), and informative (tell the bot something the existing features don't). Have an idea? Click the submission form.

Every bot receives a game state x and must return a single move from the list of legal options. All bot types share this contract — what differs is the strategy used to rank or filter those moves.

There are three broad approaches used in Learn2Ludo:

  • Priority rules — check conditions one by one and take the first move that matches a rule. No scoring, no weighing; just structured if-then logic.
  • Weighted scoring — compute a score for every legal move using a combination of features and weights, then pick the highest. Fully deterministic once the weights are fixed.
  • Learned policy — use a model trained on game outcomes to estimate which move leads to the best long-run result. The decision logic is not hand-written; it emerges from experience.
If two moves tie, the bot picks between them at random. This is the only randomness in a weighted bot's decision — everything else is deterministic.

Bots fall into three broad categories:

SDR Simple dispatching rule

Follows one priority rule. Examples: Ares (always capture if possible), Athena (stay on safe squares), Hestia (advance the furthest pawn), Artemis (activate yard pawns), Eris (random).

Predictable and easy to study. If its one rule does not apply, it falls back to random choice.

CDR Composite dispatching rule

Scores every legal move using a weighted sum of features — φ(x) · w — then picks the highest. Apollo is the built-in CDR. Custom bots you build on the Bots page are also CDRs — you control the weights with sliders.

Setting one weight to 100 and the rest to 0 turns a CDR into the matching SDR.

RL Reinforcement learning

Learns by playing thousands of games and adjusting its internal model based on wins and losses. Its decision logic is not hand-coded — it emerges from experience.

Train RL bots on the RL page. Saved models appear in the bot list.

SDR and CDR bots have fixed behaviour: their rules and weights are set before the game starts and do not change during play.

An RL bot improves through experience. During training it plays many games, receives a reward signal, and gradually updates its model to maximise future rewards. Once training is complete the model is frozen — this is called inference.

Fixed bot (SDR / CDR)
  • Rules written by hand
  • Behaviour is fully explainable
  • No training needed
  • Cannot adapt to new situations
RL bot
  • Learns from game outcomes
  • May discover non-obvious strategies
  • Requires training time
  • Harder to interpret directly
Both bot types use the same game engine and the same legal move rules. The difference is only in how they choose which legal move to make.
