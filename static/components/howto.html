How It Works

A plain-language guide to how bots make decisions in Learn2Ludo.

What is a game state?

Before a bot can decide anything, it needs to know what is happening on the board. The game state is a complete snapshot of the game at one moment in time. It contains:

  • Every pawn's current position (yard, track, home stretch, or finished)
  • Whose turn it is
  • The dice value just rolled
  • Which moves are currently legal
  • Board layout — track length, safe squares, starting squares
Think of the game state as a photograph of the board. Two identical photographs mean two identical situations — and a deterministic bot will always make the same choice given the same photograph.

What are features?

Raw board positions are hard to reason about directly. Features translate the game state into a set of numbers, one per move, that capture what matters strategically. Each feature answers one question about a candidate move.

Capture Does this move land on an opponent's pawn and send it back to their yard? +1 if yes, 0 if no
Risk How many opponent pawns can reach the destination square on their next roll? 0 – 1 (fraction of dice outcomes that threaten you)
Risk reduction Does moving this pawn lower its current exposure to capture? Positive when the move is safer than staying
Progress How much closer to home does this move bring the pawn? Higher = further ahead
Safety Does the destination land on a safe square? +1 if safe haven, 0 otherwise
Blockade Does this move stack with a friendly pawn to form a blockade? +1 if a blockade is created
Spread Does this move keep pawns spread out rather than clustered together? Positive when pawns are well distributed
Activation Does this move bring a pawn out of the yard for the first time? +1 when a yard pawn enters the track

How bots make decisions

The weighted bot (Apollo and custom bots) scores every legal move using a weighted sum of features, then picks the highest-scoring move.

Score for a move = wcapture · capture  +  wprogress · progress  +  wsafety · safety  +  …

Each weight controls how much that feature matters. A weight of 0 means the bot ignores that feature entirely. A large positive weight makes the bot strongly prefer moves that score well on it.

Example — Apollo evaluates two moves:

Safety101
Total score 5.6 ✓ chosen 2.6
If two moves tie, the bot picks between them at random. This is the only randomness in a weighted bot's decision — everything else is deterministic.

Lookahead

The decision-making described above only looks at the current board state — it scores each move and picks the best one right now. But a smarter bot could also ask: what is likely to happen next?

No lookahead (SDR / CDR)
  • Scores moves based on the current state only
  • Fast — one pass per decision
  • Cannot anticipate what an opponent will do next
1-step lookahead
  • For each candidate move, simulate the resulting board state
  • Score that state, not just the immediate move
  • Picks the move that leads to the best position one step ahead
The pawn preview you see on the board is essentially a 1-step lookahead visualised — it shows you the state that would result from each candidate move.

Lookahead is more accurate but more expensive: a bot must evaluate every legal move from the resulting state, not just the current one. The cost multiplies with each additional step.

Beyond 1-step lookahead, a bot could run a Monte Carlo simulation — play out many random games from the resulting state and use the win rate to estimate how good that position is. This gives a much richer signal than feature scores alone, at the cost of significant computation. Monte Carlo methods are not currently implemented in Learn2Ludo, but they are a natural next step on the path from simple rules to full RL.

Bot types in Learn2Ludo

Bots fall into three broad categories:

SDR Simple dispatching rule

Follows one rule. Examples: Ares (always capture if possible), Athena (stay on safe squares), Hestia (advance the furthest pawn), Artemis (activate yard pawns), Eris (random).

Predictable and easy to study. If its one rule does not apply, it falls back to random choice.

CDR Composite dispatching rule

Combines multiple features with weights. Apollo is the built-in CDR. Custom bots you build on the Bots page are also CDRs — you control the weights with sliders.

Setting one weight to 100 and the rest to 0 turns a CDR into the matching SDR.

RL Reinforcement learning

Learns by playing thousands of games and adjusting its internal model based on wins and losses. Its decision logic is not hand-coded — it emerges from experience.

Train RL bots on the Train page. Saved models appear in the bot list.

Training vs fixed behaviour

SDR and CDR bots have fixed behaviour: their rules and weights are set before the game starts and do not change during play. They are fast, transparent, and easy to understand.

An RL bot improves through experience. During training it plays many games, receives a reward signal (positive for good outcomes, negative for bad ones), and gradually updates its model to maximise future rewards. Once training is complete the model is frozen and the bot plays using what it learned — this is called inference.

Fixed bot (SDR / CDR)
  • Rules written by hand
  • Behaviour is fully explainable
  • No training needed
  • Cannot adapt to new situations
RL bot
  • Learns from game outcomes
  • May discover non-obvious strategies
  • Requires training time
  • Harder to interpret directly
Both bot types use the same game engine and the same legal move rules. The difference is only in how they choose which legal move to make.
